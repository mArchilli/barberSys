# Testing — registro de hallazgos

Hallazgos y decisiones no obvias surgidas de tests o de auditorías de performance — el contexto completo (causa, cómo se detectó, qué lo cubre), no solo el resultado final, para quien repase esto más adelante. Mismo criterio que "Hallazgos registrados" en `CLAUDE.md`, pero para lo que es específicamente de testing/performance.

## 2026-08-03 — N+1 en `BusinessMetricsService::ownersNearPlanLimit()` (panel admin)

Una auditoría de performance contra un dataset multi-tenant sembrado (220 owners, 85k+ cortes — ver `database/seeders/MultiTenantVolumeSeeder.php` y `app/Console/Commands/AuditarPerformance.php`) detectó que `admin.dashboard` ejecutaba **1589 queries** (443ms de DB) contra un puñado esperable. Causa: `ownersNearPlanLimit()` llamaba a `PlanLimitService::maxBarberias()/maxBarberos()/currentBarberias()/currentBarberos()` por cada owner dentro de un `map()`, y cada uno volvía a consultar la suscripción/barberías desde cero en vez de reusar la relación `subscription.plan` ya eager-loaded. Fix: una sola query con `with('subscription.plan')` + `withCount('barberias')`, más un agregado único (`GROUP BY barberias.owner_id`) para barberos activos — mismo patrón que ya usaba `Admin\OwnerController::index`. Medido con `php artisan app:auditar-performance` sobre el mismo dataset: **1589→15 queries, 443ms→55ms**. `PlanLimitService` no cambió de firma — sigue usado tal cual por sus otros 5 callers, todos de un solo owner por request, donde una query no es un problema.

De paso, el fix expuso un bug real: la query nueva de `barberoCounts` filtraba por `active` sin calificar la columna, ambigua después del `join` con `barberias` (que también tiene `active`). MySQL lo toleraba en silencio, resolviendo a una de las dos columnas sin avisar; SQLite —el motor de test, `phpunit.xml` fuerza `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:`— lo rechazaba con `ambiguous column name`. Lo atrapó `tests/Unit/Services/Admin/BusinessMetricsServiceQueryCountTest.php` antes de llegar a producción. Corregido calificando `users.active` explícitamente. Recordatorio general: una diferencia de comportamiento entre el motor de test y el de producción no es necesariamente un falso positivo del test — acá el test tenía razón y MySQL estaba escondiendo el bug.

## 2026-08-03 — `newOwnersOnboarding()` agregaba sobre toda la tabla `cortes` sin filtrar antes

Mismo panel, `admin.onboarding.index`: una sola query (147ms) pero pesada — 4 `leftJoinSub` agregando `MIN(created_at) GROUP BY owner_id` sobre `cortes`/`servicios`/`medios_pago`/`users` enteras antes de filtrar por los owners del rango de fecha objetivo. Fix: resolver primero los `owner_id` de los últimos 30 días (`$recentOwnerIds`), y agregar cada subquery con `whereIn('barberias.owner_id', $recentOwnerIds)` antes del `GROUP BY`.

La primera medición post-fix no mostró mejora (147ms→141ms) — no porque el fix estuviera mal, sino porque los 220 owners del seeder se habían creado todos en la misma corrida, con el mismo `created_at`: la ventana de "últimos 30 días" no excluía a nadie, así que el filtro temprano no filtraba nada (`whereIn` con ~220 de 220 owners no reduce un join). Se backdatearon 209 de los 225 owners a fechas realistas (60-400 días atrás), dejando 16 genuinamente recientes, y ahí se midió el efecto real: **147ms→34ms (~4.3x)**. Las queries suben de 1 a 2 a propósito — el costo de la query de `$recentOwnerIds` es aceptable a cambio de dejar de escanear 85k+ filas de `cortes` cuando el objetivo son 16 owners. Recordatorio: un dataset sembrado en una sola corrida puede esconder justo el problema que se está tratando de medir (todo comparte `created_at`) — conviene backdatear cuando el filtro bajo prueba es por fecha de alta.

Regresión cubierta por el mismo `BusinessMetricsServiceQueryCountTest`, con un **rango** de queries `[2, 5)` en vez de un techo único: acá un techo solo (como el del caso de arriba) no hubiera detectado una regresión, porque la versión vieja tenía *menos* queries (1), no más — el bug era de scope, no de cantidad de roundtrips.
